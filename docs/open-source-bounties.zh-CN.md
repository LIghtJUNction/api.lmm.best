# 开源悬赏玩法说明

## 一、这是什么

“开源悬赏”是面向公开 GitHub 项目的真实缺陷修复激励机制。

项目发布者可以使用自己的 API 余额预先托管若干份修复奖励，并支付平台公开展示的低比例任务手续费；贡献者可以接受挑战，并提交可复现的 Issue、对应修复 PR 或两者。项目发布者审核通过后，系统会将锁定的奖励直接划转到贡献者的 API 余额。

本玩法独立于 Challenge II 恢复流程。平台不会预置、默认发布或自动置顶任何项目，包括 `LIghtJUNction/api.lmm.best`。所有项目都必须由发布者主动创建并使用自己的余额发布；站长、管理员和普通用户适用完全相同的扣费规则。

## 二、核心原则

1. 只奖励真实、可复现的代码缺陷。
2. 已提交的 Issue 或 PR 必须属于悬赏指定的 GitHub 仓库。
3. 提交 PR 时，PR 必须聚焦于悬赏目标，并提供适当的测试或验证；同时提交 Issue 时，应在 PR 中关联该 Issue。
4. 发布悬赏时一次性扣除管理员配置且公开展示的任务手续费，并锁定完整奖励池。
5. 每日签到奖励直接进入统一余额，可以抵扣部分或全部任务手续费。
6. 关闭项目时只退回尚未使用的托管奖励，已收取的任务手续费不退还。
7. 审核通过后，奖励直接从托管余额划转到贡献者余额，同一提交只能支付一次。
8. 低质量报告、伪造缺陷、重复 Issue、无关 PR、机械式垃圾提交和纯粹为领取奖励制造的改动均不符合资格。

## 三、发布者怎么玩

### 1. 创建草稿

进入“个人”栏目，在“提交工单”下方打开“开源悬赏”，选择“创建悬赏”。填写：

- GitHub 仓库链接；
- 悬赏标题；
- 项目与缺陷范围；
- 验收和验证规则；
- 每项修复奖励；
- 奖励名额。

创建和编辑草稿不扣费，也不会出现在悬赏广场。

### 2. 发布并托管奖励

发布时的总扣费为：

`每项修复奖励 × 奖励名额 + 任务手续费`

其中：

- 奖励池进入系统托管，只能用于审核通过后的奖励划转或项目关闭后的未使用额度退款。
- 任务手续费由管理员设置并向所有用户公开，按完整奖励池的一定比例计算，默认低费率为 1%。费率快照随项目保存；手续费不从贡献者奖励中扣减，也不随项目关闭退款。
- 每日签到获得的奖励会直接增加同一账户余额，因此可用于支付部分或全部任务手续费，不需要单独兑换。
- 发布者余额不足时无法发布。
- 站长或管理员发布自己的项目时也必须从自己的账户余额扣费，没有免费或豁免通道。

### 3. 管理进行中的悬赏

发布后，发布者可以：

- 暂停：暂时停止新的挑战接受，已接受的挑战仍保留；
- 恢复：重新开放剩余名额；
- 查看全流程：查看参与者、Issue、PR、完成备注、评审结果和余额流水；
- 给小费：即使贡献者只完成了部分有价值的工作，也可以从自己的余额即时支付小费，帮助其保持动力；
- 关闭：结束悬赏并退回未使用的托管奖励。

如果仍有处于“已接受”或“已提交”状态的挑战，系统会阻止关闭。发布者必须先完成审核，或由贡献者退出挑战。

拒绝挑战后有 7 天申诉期。申诉期内即使尚未创建争议，受影响的奖励名额和托管资金也保持冻结，发布者不能立即关闭退款或把同一份托管额度分配给其他人。贡献者发起争议后继续冻结，直到第三方管理员裁决；驳回申诉或 7 天到期且无人申诉后才释放。

### 4. 审核与划转

贡献者提交成果后，发布者应核验：

- 提交 Issue 时，Issue 是否描述了真实且可复现的代码缺陷；
- 提交 Issue 时，Issue 是否包含受影响项目、复现步骤、预期行为、实际行为和影响；
- 同时提交 Issue 和 PR 时，PR 是否关联对应 Issue；
- 提交 PR 时，PR 是否只处理悬赏目标，没有混入无关改动；
- 修复是否有效，并包含合理的测试或验证；
- 已提交的 Issue 或 PR 是否属于悬赏指定仓库；

审核结果有两种：

- 批准并划转奖励：系统从托管奖励池扣除一份奖励，直接增加到贡献者余额；该操作具备幂等保护，不能重复支付。
- 拒绝提交：暂不支付奖励并进入 7 天申诉期；申诉期内奖励和名额保持托管，防止发布者拒绝后立即退款。申诉被第三方驳回，或到期且无人申诉后，名额才会释放。

当全部奖励名额都已审核通过后，项目自动完成。

审核时发布者必须给贡献者填写 1–5 分和公开评价。评分、评语及贡献者的历史平均分会同时向双方和争议管理员展示，不能用私下低分替代事实依据。

## 四、贡献者怎么玩

### 1. 接受挑战

在悬赏广场选择一个仍有可用名额的项目，点击“接受挑战”，填写自己的 GitHub 用户名。

接受后，系统会为该贡献者预留一份奖励名额。同一用户不能重复接受同一个悬赏。

项目发布者不能接受自己发布的悬赏。

### 2. 发现并记录真实缺陷

如果提交 Issue，应在指定 GitHub 仓库创建有效 Issue，并至少说明：

- 受影响的项目或模块；
- 可重复执行的复现步骤；
- 预期行为；
- 实际行为；
- 缺陷造成的影响。

不要先制造问题再提交修复，也不要提交重复、无法复现或仅属于使用咨询的 Issue。

### 3. 提交聚焦的修复

如果提交 PR，应确保该 PR：

- 同时提交 Issue 时，在 PR 中关联该 Issue；
- 只修改解决该缺陷所需的内容；
- 补充适当的自动化测试、回归测试或可核验的验证步骤；
- 属于悬赏指定仓库。

同一个 PR 不能重复用于领取奖励。

### 4. 在系统中提交

回到“开源悬赏 → 我接受的挑战”，提交：

- GitHub Issue 链接或 GitHub PR 链接，至少填写一项，也可以两项都填；
- 可选的完成备注。

系统会校验已填写的 Issue 或 PR 是否属于悬赏仓库，并阻止重复提交同一个 PR。

### 5. 发布者直接审核和到账

接单人提交后，任务发布者直接审核已提交的 Issue、PR 和完成备注。审核通过后，奖励会直接进入贡献者的 API 余额，可用于平台支持的模型。

如果提交被拒绝，贡献者可以在 7 天内发起争议。此期间奖励仍在托管、名额仍被占用；到期未申诉或申诉被驳回后，挑战才最终结束且名额可由其他贡献者接受。

贡献者也可以在审核完成前退出挑战。退出后，预留名额会被释放，但已投入的开发时间不由平台补偿。

审核完成后，贡献者可以对发布者/验收者给出 1–5 分和公开评价。发布者信誉会展示在悬赏广场，接单人的信誉会展示在验收界面。双方的单次评价、评语、历史平均分和评价数互相可见，用持续公开的信誉成本约束拒付、恶意低分或敷衍交付等不诚实行为。

## 五、部分工作与小费

小费是正式悬赏奖励之外的即时转账：

- 发布者可以在挑战未退出时给贡献者小费，包括尚未达到完整验收标准但已经完成部分有价值工作的情况；
- 小费从支付者自己的余额扣除，直接进入贡献者余额；
- 小费不占用、不减少托管奖励，也不代表正式验收通过；
- 小费一旦发送不可退款，发送前网页端和 MCP 都要求明确确认金额、对象和影响；
- 争议管理员能看到累计小费，以便完整理解双方已经发生的资金往来。

## 六、争议工单和第三方介入

当悬赏付款或验收发生争议时，任一当事人都可以从挑战卡片进入“提交工单”，选择“开源悬赏争议”并填写挑战 ID、争议原因、标题和事实陈述。普通退款、技术、账单等工单仍通过邮件提交；开源悬赏争议会持久化到系统，由第三方管理员处理。

被拒绝的贡献者必须在拒绝后的 7 天内发起争议。系统在这段时间预留托管资金和奖励名额，因此发布者不能通过“先拒绝、立即关闭退款”消灭申诉机会。同一当事人对同一挑战只能创建一次最终争议案件，已裁决案件不能反复重开冻结资金；另一方仍可在没有其他待处理案件时创建自己的案件。

适用场景包括：

- 修复已经合并、达到公开要求，但发布者最后拒绝支付；
- 提交符合约定却被拒绝；
- 发布后临时改变或误导验收要求；
- 骚扰、侮辱或其他不当行为；
- 其他需要中立核验的悬赏分歧。

系统会根据挑战 ID 自动关联可信的后端记录，而不是相信 URL 查询参数中的身份或金额，包括：项目和仓库、Issue、PR、原始提交和验收意见、奖励、小费、托管流水、双方评分与公开评语。

争议打开后：

- 双方都能看到“等待第三方处理”状态和原始争议陈述；
- 受影响的托管奖励和奖励名额冻结，不能关闭退款、释放或重复使用；
- 双方仍可看到已有评分和信誉历史，以便识别长期行为模式；
- 管理员必须分别保留原始验收理由、争议陈述和管理员结论，不能用结论覆盖原始证据。

管理员核验后可作出两类裁决：

- 从托管支付：确认已提交的 Issue、PR 和完成情况成立后，从项目托管余额强制向接单人划转正式奖励，挑战变为已批准。该事务只能执行一次；
- 驳回申诉：不划转正式奖励，并记录中立的管理员结论。驳回只表示当前证据不足或主张不成立，不自动等于申诉人不诚实。

裁决管理员必须是真正的第三方：如果管理员本人是该悬赏的发布者或接单人，系统会在同一数据库事务中拒绝其支付和驳回操作，不能自付或自拒。裁决结论、处理状态和处理时间对双方可见。支付和驳回在网页端与 MCP 中均必须二次确认。

## 七、MCP 全自动支持

每个用户可以生成独一无二的个人 MCP Token，以 Bearer Token 访问站点 `/mcp` 端点。服务遵循 MCP `2026-07-28` 规范并使用无状态 Streamable HTTP；数据库只保存令牌摘要，明文只在生成或轮换时显示一次，也可以随时吊销。

网页端提供一键复制 AI 提示词，包含端点、当前 MCP 规范版本、鉴权方式和完整操作原则。MCP 覆盖创建草稿、发布、接单、提交证据、验收、支付、拒绝、小费、双方评分、发起争议、查询争议和管理员裁决等全生命周期。

凡涉及余额、托管、退款、删除、退出、公开评分或争议裁决的敏感操作，AI 必须先向用户展示准确动作、对象、证据、手续费和余额影响，并取得显式确认后才能继续。确认状态与用户、工具和规范化参数绑定，短时有效、一次性消费。发布、验收付款、拒绝、关闭退款、小费、评分、争议创建/裁决、草稿删除和退出接单都会在业务变更的同一事务中保存操作结果；响应丢失时重试会返回已提交结果，而不会重复扣费、转账、评分或冻结。

## 八、余额与退款规则

假设发布者设置：

- 每项修复奖励：20；
- 奖励名额：3；
- 管理员任务手续费：2.5%。

发布时一次性扣除：

`20 × 3 + 60 × 2.5% = 61.5`

资金流转如下：

- 60 进入奖励托管池；
- 1.5 作为平台任务手续费，不可退款；
- 每日签到奖励已进入发布者统一余额，可直接抵扣这 1.5 手续费；
- 每批准一个有效修复，从托管池向贡献者余额划转 20；
- 如果批准 1 个修复后关闭项目，剩余 40 退回发布者余额；
- 已划转给贡献者的 20 和平台任务手续费均不退回。

系统会记录平台任务手续费、奖励托管入账、正常/争议奖励划转、小费转账和托管余额退回等流水。

## 九、状态说明

### 项目状态

- 草稿：尚未扣费和公开展示；
- 已发布：正在悬赏广场展示，可接受挑战；
- 已暂停：不再接受新的挑战；
- 已完成：全部奖励名额都已支付；
- 已关闭：人工结束，未使用的托管奖励已退回。

### 挑战状态

- 已接受：贡献者已预留名额，尚未提交证据；
- 已提交：Issue 或 PR 以及完成备注已提交，等待审核；
- 已批准：审核通过，奖励已经划转；
- 已拒绝：审核未通过，未支付奖励；拒绝后 7 天内奖励和名额仍为申诉保留，申诉驳回或到期后释放；
- 已退出：贡献者主动退出，名额已释放。

### 争议状态

- 待处理：证据、奖励名额和受影响托管资金已冻结，等待第三方管理员核验；
- 已支付解决：管理员确认应付款，并已从托管强制划转；
- 已驳回：管理员未批准争议付款，并已记录双方可见的处理结论和时间。

## 十、不符合奖励资格的情况

以下情况包括但不限于：

- 无法复现或没有实际影响的问题；
- 伪造、刻意制造或夸大缺陷；
- 已存在的重复 Issue；
- 与 Issue 无关或范围明显失控的 PR；
- 只有格式化、依赖刷新、批量替换等机械改动；
- 缺少必要测试或无法验证修复效果；
- 已提交的 Issue 或 PR 与悬赏仓库不一致；
- 重复提交同一个 PR；
- 垃圾信息、批量骚扰或自动化刷奖励；
- 主要目的只是获取奖励，而非解决真实工程问题的改动。

正常验收首先由项目发布者负责；发生争议时，以平台第三方管理员基于系统证据作出的结论为准。

## 十一、简版宣传文案

发现真实 Bug，写清复现步骤，提交对应 Issue 和修复 PR。通过项目发布者审核后，托管奖励会直接划转到你的 API 余额。

任何人都可以用自己的余额发布开源悬赏，包括站长本人。平台不设置默认项目：奖励在发布时全额托管，只收取管理员配置并公开展示的低比例任务手续费，每日签到奖励可直接抵扣。支持部分工作小费、双向公开信誉和第三方争议工单；修复已合并却拒付时，管理员可核验证据并从托管强制划转。
